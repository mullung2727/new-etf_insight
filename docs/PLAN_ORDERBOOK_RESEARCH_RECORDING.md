# PLAN — 호가창 리서치용 호가·체결 녹화

한 줄: 호가창 전략 리서치(잔량 불균형·매도벽 흡수·체결 흐름·스프레드)를 위해 선별 종목의 **실시간 호가(0D)와 체결(0B)을 장 전체 시간** 녹화한다.
종목 선별 기준은 아직 모른다 — **P0 실측(등록 한도·용량·유실) → 사용자와 같이 기준 결정 → P1 구현** 순서로 간다.

## 0. 왜

- 2026-10-06 스프레드 조사(체결 조회 `ka10003`, 200종목 오전 2.6시간)에서 시장조성·몰림 추종·몰림 중 매수호가 받기 모두 비용 후 음수 또는 판정 불가.
  판정을 막은 건 데이터: 체결 조회는 1초 단위라 체결 직전/직후 호가를 못 가리고(3종목 대조 결과 넓은 스프레드 체결의 48%가 체결이 만든 순간 확대),
  내 지정가의 대기열 위치·양쪽 체결 가능성을 재현할 수 없다.
- 리서치 대상은 스프레드만이 아니라 호가창 전략 전반(아래 §2). 공통으로 **같은 종목의 호가 변화 + 체결 1건씩**이 같은 시계로 필요하다.
- 호가 데이터가 크므로 전종목은 불가 → 종목 선별이 필요하고, 그 기준을 정할 근거(한도·용량)를 아직 모른다.

## 2. 연구할 호가창 전략 (선별 기준의 입력)

| 전략 | 필요 데이터 | 맞는 종목 유형 | 출처 |
|---|---|---|---|
| 최우선 잔량 불균형 → 수 초~수 분 방향 | 0D | 체결이 잦은 중간 이상 유동성 | 문헌 (Cont 외 2010) |
| 체결 흐름 불균형(OFI) | 0D + 0B | 위와 같음 | 문헌 |
| **매도벽 흡수**: 큰 매도잔량을 시장가 매수가 먹는 속도 → 상승 | 0D + 0B | 매도벽이 자주 서는 종목 | **사용자 가설** |
| 깊은 호가(2~10단) 기울기 | 0D 10단 | 중간 유동성 | Cao·Hansch·Wang |
| 넓은 스프레드 시장조성(재확인) | 0D + 0B | 저유동·스프레드 2%+ | 2026-10-06 조사 |
| 운영 전략 진입 시점 개선(종가베팅·high52·유증) | 0D + 0B | 실제 매매 후보 종목 | 내 판단 |

비용 현실: 효과 대부분이 수 초~수 분이고 왕복 비용 0.35%(`research/backtest_daily/stats.COSTS`)를 넘기 어렵다 → 단독 단타보다 진입 시점 개선 용도가 현실적일 수 있음(내 판단, 검증 대상).

## 3. P0 실측 — 기준을 정하기 위한 숫자

장중 1회, 실매매 연결을 건드리지 않는 방식으로 잰다(§5 연결 분리 결정 전이므로).

| 측정 | 방법 | 이 숫자로 정하는 것 |
|---|---|---|
| 웹소켓 등록 한도 | 0D·0B 를 종목 10개씩 늘려 등록, "등록 한도 초과" 나는 지점. 0D+0B 가 한도를 같이 쓰는지 | 최대 종목 수 N |
| 종목당 하루 용량 | 유동성 구간별(상·중·하) 각 3종목, 30분 0D+0B 원본 이벤트 수·바이트 → 6.5시간 환산 | N 종목 × 일수 → 월 디스크 |
| 유실 | broker `dropped` 카운트, 종목 수 늘릴 때 변화 | 실제 받을 수 있는 N |
| 0B 필드 | 실시간 체결 프레임 필드(체결가·부호 수량·체결시각 정밀도·최우선호가 포함 여부) 실측 | 직전/직후 호가 판정 가능 여부 |

- 측정 수단: 연구용 별도 broker 연결(§5 결정 대기). 결정 전이면 장 마감 후 등록 한도만 먼저(등록 ACK 는 장외에도 응답하는지 P0 에서 확인).
- **2026-10-06 장외 측정 완료**: 등록 ACK 는 장외에도 응답. 그룹당 200, 두 번째 연결 공존 확인(§1). 남은 P0: 장중 용량·유실·0B 필드, 그룹 여러 개로 200 넘게 되는지.
- **2026-10-08 장중 측정**(50종목, 상 20·중 15·하 15, 연결 1개): 용량·유실·0B 필드 완료(§1). 12분 만에 1006 끊김 → 그룹 여러 개 시험 못 함.
- **2026-10-12 예정**: 연결 2개 동시(40종목 / 10종목) 장 전체 + 재접속 — 끊김이 수신량 때문인지(많이 받는 쪽만 끊기는지), 같은 앱키 3번째 연결 허용 여부. `ws_split.py`, 작업 `ws-split-20261012`.
- 산출: `research/orderbook_capacity/README.md` 표 1장.

## 4. 종목 선별 — 같이 정할 것 (P0 숫자 나온 뒤)

정해야 할 질문과, 각 질문에서 P0 숫자가 하는 역할. 답은 비워둔다.

1. **몇 종목?** — **결정: 50종목으로 시작 (사용자 2026-10-07).** 근거: 그룹당 한도 200 안. 장중 실측(10-08) 원문 4.5GB/일이지만 아래 §5 저장 방식(필요 필드·parquet)이면 하루 약 0.06GB·월 1.3GB → 용량은 제약이 아님.
2. **같은 종목을 계속(고정 패널) vs 날마다 바꿈(이벤트)?**
   - 고정: 날짜 기준 walk-forward 검증 가능, 종목 특성 통제. 대신 사건(급등·매도벽)이 드물게 잡힘.
   - 이벤트: 사건은 많이 잡힘. 대신 선정 자체가 미래 정보를 쓰지 않도록 **전일 정보 또는 장중 그 시각까지 정보로만** 골라야 함.
   - 혼합 비율이 실제 결정 사항.
3. **고정 패널을 어떻게 고르나?** — 후보 축: 거래대금 구간, 스프레드 구간(2026-10-06 조사값), 시가총액, 매도벽 빈도(P0 이후 데이터로만 측정 가능).
   §2 전략별로 맞는 유형이 달라 "구간별 고르게"가 기본안 후보.
4. **운영 전략 후보 종목을 포함할까?** — 진입 시점 개선 리서치에 바로 쓰임. 기존 녹화기 20종목과 겹침.
5. **얼마나 오래?** — walk-forward 최소 단위(예: 학습 N일 + 검증 M일)에서 역산.

결정 방식: P0 표 + 각 질문별 선택지·결과·추천을 내용으로 풀어 사용자와 한 질문씩 정한다. 결정은 §7 결정 출처 표에 기록.

## 5. P1 녹화 구현 (선별 기준 확정 후 상세화)

확정 가능한 것만 적는다.

- broker: 0B 등록·해제·재접속 복구를 0D 와 같은 방식으로 (`broker/kiwoom/ws/manager.py`), 이벤트 버스로 녹화기에 전달.
- 녹화기: 0B 이벤트를 원본 월별 파일에 append (0D 원본과 같은 파일·같은 시계 `_recv_ts`), 리서치 종목은 기존 매매 후보 목록과 별도 config 키.
- 녹화 시간: 리서치 종목은 09:00~15:30 전체 (기존 매매 후보 창은 그대로).
- **저장 위치 (사용자 2026-10-07)**: 장중에는 C:(SSD, 여유 37GB)에 기록 → 장 마감 뒤(예: 16:00) D: 외장하드(USB HDD, 여유 581GB)로 **이동**.
  - 이유: 장중 USB 절전·순간 끊김으로 녹화가 깨지는 위험을 피하고, C: 에는 하루치만 머묾.
  - 리서치 원본 파일은 **일 단위**(`orderbook_raw_YYYYMMDD.sqlite3`)로 바꾼다 — 현재 월 단위 덧붙이기 파일이면 하루치만 옮기기 복잡.
  - **장중 C: 저장 형식 (2026-10-08 실측 근거)**: 키움 원문 JSON 은 저장하지 않고, 받은 즉시 필요한 필드만 정수로 뽑아 일 단위 sqlite 두 테이블에 쓴다.
    - `trade`(0B): `rt`(수신 ns) · `code` · `t`(FID 20) · `price`(10, 절대값) · `qty`(15, 부호 유지) · `cum_vol`(13) · `ask1`(27) · `bid1`(28)
    - `book`(0D): `rt` · `code` · `t`(21) · 매도·매수호가 1~10(41~60, 절대값) · 잔량 1~10(61~80) · 총잔량(121·125)
    - 필드 매핑은 10-08 원문으로 확인(`compact_size.py`, 누적거래량 증가 = 체결량 대조 통과).
    - 대가: 지금 버리는 FID(체결강도·예상체결 등)는 나중에 필요해도 복원 불가. 원문 gz 를 남기면 하루 0.75GB(월 16GB)라 기본은 버림.
  - **마감 후 변환·이동·삭제 (사용자 2026-10-08 "외장하드로 변환, 이 서버 하드에서는 삭제")** — 스케줄 작업 1개, 장 마감 뒤(예: 16:10) 실행:
    1. C: 에 남은 **모든** 일 파일(`orderbook_raw_YYYYMMDD.sqlite3`, 오늘 것 포함·이전 실패분 포함)을 날짜 순으로 처리. 녹화 중인 오늘 파일은 녹화기 종료(15:30 창 끝) 확인 후에만.
    2. duckdb 로 테이블별 `ORDER BY code, rt` 정렬 → parquet zstd 로 D: 에 쓴다:
       `D:\orderbook\YYYY\MM\trade_YYYYMMDD.parquet`, `book_YYYYMMDD.parquet`, `gaps_YYYYMMDD.parquet`(끊긴 구간, 아래 재접속). 먼저 `.tmp` 이름으로 쓰고 검증 통과 후 이름 변경(반쯤 쓴 파일이 정상 파일로 보이지 않게).
    3. 검증: 테이블별 행 수, 종목 수, `rt` 최소·최대, 종목별 `sum(qty)`·`count` 가 sqlite 와 parquet 에서 같은지. parquet 을 **다시 읽어서** 비교.
    4. 전부 같으면 C: sqlite 삭제. 하나라도 다르거나 D: 미연결·여유 공간 부족(필요량의 3배 미만)이면 **삭제하지 않고** C: 에 두고 batch 채널 알림 → 다음 실행 때 재시도.
    5. 같은 날 parquet 이 이미 D: 에 있으면(재실행) 덮어쓰지 않고 3번 검증만 해서 같으면 C: 삭제, 다르면 알림(사람이 판단).
    6. C: 에 남은 일 파일이 3일치 이상 쌓이면 경고(외장하드 장기 미연결 감지). C: 하루 sqlite 약 0.4GB → 여유 37GB 로 수십 일은 버팀.
  - 리서치는 D: parquet 을 duckdb 로 바로 읽는다(`read_parquet('D:/orderbook/*/*/trade_*.parquet')`). 무거운 전 기간 분석만 필요한 달을 C: 로 복사.
  - 용량(10-08 실측 환산): parquet 하루 약 0.06GB, 월 약 1.3GB, D: 여유 581GB → 수년.
  - 기존 1초 스냅샷 DB(`orderbook.sqlite3`, 41MB)는 C: 유지.
  - **복사본 (사용자 2026-10-07)**: D: 는 월 1회 DB 백업도 받는 같은 디스크라 원본 호가가 한 곳에만 있게 됨 →
    - 기본: **백업용 외장하드 1대 추가**(2TB, 20만 원 미만). 평소 PC 에서 분리 보관(과전압·랜섬웨어가 두 디스크를 함께 망가뜨리지 않게),
      월 1회 백업 때 연결해 D: 의 지난 달 일 단위 parquet 을 복사. 최근 한 달치는 D: 에만 있음 — 리서치 데이터라 감수.
    - 막지 못하는 것: 화재·도난 등 같은 장소 사고.
    - 옵션(필요 시): 다른 장소(사용자 확보 가능)에 NAS 또는 상시 PC 를 두고 Syncthing 동기화 → 장소 사고까지 대비.
      검토한 유료 클라우드(2026-10-07 검색 기준, 공식가 미확인): Hetzner Storage Box 1TB 월 €3.2+VAT, Backblaze B2 TB당 월 $6.95(10GB 무료),
      Google One 200GB 월 3,700원, MS 학생 OneDrive 100GB 무료(계정 만료·관리자 축소 위험).
- **미결 — 연결 분리**: 리서치 0D/0B 를 실매매 체결 통보(00)와 같은 :8001 웹소켓에 태울지, 별도 연결(예: :8002 계좌 broker 또는 리서치 전용 프로세스)로 뺄지.
  같은 연결이면 0B 폭주 시 00 지연·유실 위험(실매매). P0 유실 측정 후 결정. 내 추천: 분리.
  - 10-08: 별도 연결은 장중에도 broker 를 끊지 않았음(12분). 10-12 연결 2개 시험 결과로 확정.
- **재접속 필수**: 10-08 별도 연결이 12분 만에 끊김 → 녹화기는 끊기면 다시 붙고 0B+0D 재등록, 끊긴 구간(시작·끝 수신 시각)을 `gaps` 테이블에 기록해 리서치가 그 구간을 뺄 수 있게.

## 6. 요구사항 → 테스트

| 요구사항 | 테스트 |
|---|---|
| 리서치 녹화가 실매매 체결 통보를 막지 않는다 | 0B 다량 주입 중 00 이벤트 지연·유실 0 (연결 분리 결정에 따라 형태 확정) |
| 0B 가 0D 와 같은 시계로 저장 | 같은 `_recv_ts` 기준, 이벤트 순서 보존 단위 테스트 |
| 재접속 시 0B 등록 복구 | `manager` 재접속 테스트에 0B 목록 복구 추가 |
| 등록 한도 초과 시 녹화기 전체가 멈추지 않음 | 일부 종목 REG 실패 → 나머지 계속 녹화 |
| 기존 매매 후보 녹화(창·종목·스냅샷) 변화 없음 | 기존 녹화기 테스트 전부 통과 |
| 선정에 미래 정보 금지(이벤트 종목) | 선정 함수 입력이 전일/당시각까지 데이터뿐임을 테스트 (기준 확정 후) |
| 0B·0D 프레임 → 정수 필드 변환 | 10-08 원문 예시 프레임으로 `+`·공백·부호 처리, 절대값 컬럼, 빈 값 NULL |
| 변환 검증 통과 시에만 C: 삭제 | 행 수 1건 다르게 만든 parquet → C: 파일 남고 알림 |
| D: 미연결·공간 부족이면 삭제 안 함 | 출력 경로 없음/여유 부족 모의 → C: 그대로, 알림 1회 |
| 반쯤 쓴 parquet 이 정상 파일로 남지 않음 | 쓰기 중 예외 → `.tmp` 만 남고 최종 이름 없음, 다음 실행이 정리 후 재처리 |
| 재실행 멱등 | 같은 날 parquet 이 이미 있고 같으면 덮어쓰기 없이 C: 삭제, 다르면 삭제 안 하고 알림 |
| 밀린 날짜 처리 | C: 에 3일치 → 날짜 순 모두 처리, 3일 이상 남으면 경고 |
| 녹화 중 파일 건드리지 않음 | 녹화 창 안에서 실행 → 오늘 파일 건너뜀 |
| 재접속 후 재등록·끊긴 구간 기록 | 서버 종료 모의 → 재연결·0B+0D 재등록, `gaps` 1행(시작·끝) |
