## 2. 스키마

한국 DB와 테이블·컬럼 이름을 맞춰, 기존 쿼리 뼈대(`_BASE_SQL` 의 `ms` 순번·연속성 가드)를 그대로 쓸 수 있게 한다.

```sql
ohlcv (
    date          VARCHAR,   -- YYYYMMDD, 뉴욕 기준 거래일
    ticker        VARCHAR,   -- 야후 심볼 (BRK-B 처럼 '-' 표기)
    market        VARCHAR,   -- NASDAQ / NYSE / AMEX / ARCA / BATS
    open, high, low, close   DOUBLE,   -- 분할 반영, 배당 미반영, USD
    volume        BIGINT,    -- 분할 반영
    trading_value DOUBLE,    -- close × volume (추정치, 분할과 무관한 값)
    market_cap    DOUBLE,    -- 원 종가 × 그날 기준 최근 공시 주식수
    list_shrs     BIGINT,    -- 그날 이전 가장 최근 원 주식수
    PRIMARY KEY (date, ticker)
)
splits      (ticker, date, ratio)          PK (ticker, date)   -- 원 종가 복원·재적재 판단용
stock_names (code, name, updated_at)       -- 한국 DB와 같은 테이블. 목록의 Security Name
```

**한국 DB와 다른 점 — 리서치 코드가 반드시 알아야 할 것**

| 항목 | 한국 | 미국 | 리서치 코드 영향 |
|---|---|---|---|
| 가격 | 원가격 | 분할 반영 | **`_ADJ` 보정 금지.** 원 주식수는 분할 때 튀므로 `_ADJ` 를 걸면 이중 보정된다 |
| 가격 타입 | INTEGER | DOUBLE | 센트 단위 |
| 거래대금 | KRX 실값 | 종가×거래량 추정 | 유동성 하한을 달러로 다시 정해야 함 |
| 가격제한폭 | ±30% | 없음 | 상한가 매수불가 규칙·일간 수익률 ±30% 클립은 적용 대상 아님 |
| 휴장일 | `holidays` 자기학습 | 테이블 없음 | 야후는 거래일만 준다. `ms` 는 `SELECT DISTINCT date` 로 똑같이 만든다 |
| 스팩 | 이름에 `스팩` | 이름에 `Acquisition Corp` | DB엔 넣고 리서치에서 거른다(한국과 같음). 목록 기준 639개 |

## 3. 수집 로직 — `build_us_ohlcv.py`

한국은 **날짜 단위**(하루 전 종목)로 받지만 야후는 **종목 단위**(기간)로 준다. 그래서 멱등 기준이 "적재된 날짜"가 아니라 "종목별 마지막 적재일"이다.

| 단계 | 함수 | 동작 |
|---|---|---|
| 1 목록 | `load_universe()` | `nasdaqtraded.txt` 받기. `Nasdaq Traded=Y`, `ETF=N`, `Test Issue=N`, 이름에 Warrant/Unit/Right/Preferred/Depositary 없음, 심볼에 `$ . ^ =` 없음. 여기에 SPY·QQQ·IWM 추가. 이름은 `stock_names` 에 upsert |
| 2 구간 결정 | `plan_fetch()` | 종목별 `max(date)`. 없으면 `[시작일, 오늘)`, 있으면 `[마지막 적재일, 오늘)`. 같은 구간끼리 묶는다 |
| 3 받기 | `fetch_batch()` | `yf.download(tickers=200개, auto_adjust=False, actions=True)`. 호출 성공 여부와 별개로 요청 티커별 반환 여부를 검사한다. 미반환·빈 결과 티커는 실패 목록에 기록하고 다음 실행에서 다시 받는다 |
| 4 정리 | `to_rows()` | OHLC가 NaN인 행 버림. **뉴욕 기준 오늘 날짜 행 버림** (장중 미완성 봉). `trading_value = close × volume` |
| 5 분할 재적재 | `ensure_ohlcv()` | 새로 받은 구간에 분할이 있으면 야후가 과거 가격을 전부 다시 조정한 것이므로, 그 종목은 `[시작일, 오늘)` 전체를 다시 받는다. 전체 구간 수신·정리 성공을 확인한 뒤 **한 트랜잭션에서 DELETE 후 INSERT**하고 `splits` 에 기록한다. 실패하면 기존 행을 그대로 보존한다 |
| 6 적재 | `_insert_rows()` | 한국과 같은 스테이징 임시테이블 → `INSERT OR REPLACE` |
| 7 주식수·시총 | `ensure_shares()` | 최초 적재에서는 종목당 `get_shares_full` 1회 → 날짜별 as-of(그날 이전 최신값) 매칭. 일일 증분 행은 DB의 직전 `list_shrs`를 승계하고, 별도 주기 전체 갱신에서 이력을 다시 받아 보정한다. 원 종가 = 분할 반영 종가 × (그날 이후 분할 비율의 곱). `market_cap = 원 종가 × list_shrs`. 빈 결과는 오류로 만들지 않고 `NULL` 허용 |
| 8 정합성 점검 | `audit_gaps()` | SPY의 적재 거래일을 미국 시장 기준 달력으로 삼아 종목별 중간 누락일을 찾는다. 단순 `max(date)`로 발견할 수 없는 누락을 보고하고, 누락 종목은 누락 최초일~오늘 구간을 다시 받아 upsert한다. 거래정지·상장 전·상폐 후 구간은 오류로 확정하지 않는다 |

- **목록에서 사라진 종목(상폐)은 더 받지 않지만 기존 행은 지우지 않는다.** 이게 앞으로의 생존편향을 막는 유일한 장치다.
- 주식수 최초 전체 조회는 약 31분으로 예상한다. 일일 적재에서는 새 행에 직전값을 승계해 전 종목 API 재호출을 피한다. 별도 주기 전체 갱신 일정은 D4와 함께 정한다.
- 배치 호출이 정상 종료돼도 일부 티커만 빠질 수 있으므로, 성공/실패 통계는 배치가 아니라 **티커 단위**로 낸다.
- SPY 자체가 비었거나 최신 완료 거래일까지 적재되지 않았으면 정합성 점검을 실패 처리하고, 불완전한 달력으로 누락을 확정하지 않는다.

CLI (한국 스크립트와 같은 모양):

```powershell
# etl/ 에서
uv run python scripts/build_us_ohlcv.py --from 20240101            # 초기 적재
uv run python scripts/build_us_ohlcv.py                            # 이어받기
```

## 5. 알려진 한계

- **생존편향 (2024-01 ~ 스케줄 시작일).** 이 구간에 상폐된 종목은 야후가 안 줘서 없다. 규모는 무료 소스에 상폐 목록이 없어 **측정 불가**. 신고가·돌파 전략은 망한 종목이 빠질수록 좋게 나오므로 결과를 **상한으로** 읽는다.
- **티커 재사용·변경.** 재사용은 옛 회사가 빠지는 쪽(생존편향과 같은 방향)으로 관측됐다. 티커 변경 종목이 새 티커 아래 과거까지 이어지는지는 P2에서 샘플로 확인한다.
- **거래대금은 추정치.** 종가×거래량이라 장중 가격 분포를 반영하지 못한다.
- **야후 데이터 품질.** 비공식 API라 가끔 튀는 값·빈 날이 섞인다. P2 검증에서 샘플로 대조한다.
