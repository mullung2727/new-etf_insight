# 증권사 리포트 전 종목·섹터보고서 적재 Implementation Plan

**Goal:** 네이버 종목분석에 표시된 일부 리포트만 받는 현행 배치를, 정의된 출처의 모든 종목 보고서와 섹터/산업 보고서를 빠짐없이 발견·원본 저장·검색 가능한 체계로 확장한다. '모든 증권사가 발행한 모든 문서'라는 무한한 보장은 하지 않고, 수집원별 범위와 누락을 관측 가능하게 만든다.

**Architecture:** 출처별 목록 어댑터 → 문서 메타데이터 카탈로그/발견 이력 → 멱등 PDF 원본 저장 → 문서형 분류·종목 연관관계 → 검색/열람. 기존 일일 네이버 종목 배치와 PDF/목표가 파싱은 유지하면서 분리·확장한다. 섹터 문서는 원본 1개와 종목 N개 관계로 표현하고, 종목별 목표가 수치화는 별도 정책 승인 전까지 금지한다.

**Tech Stack:** 기존 Python ETL, Windows Task Scheduler/PowerShell, SQLite(`etl/db/report_metrics.sqlite3`), FastAPI(:8000), Next.js `broker-web`(:3100). 새로운 수집원 API나 인증 방식은 현장 검증 후 선택한다.

## 1. 문제와 확인된 사실 (2026-09-29 조사)

- `ops/scheduled-tasks/run-naver-research.ps1`은 매일 18:00 KST에 `etl/scripts/download_naver_research.py --date <당일>`을 호출한다. `list_reports()`는 `https://m.stock.naver.com/api/research/company`의 날짜 일치 항목 중 **6자리 `itemCode`가 있는 것**만 수집한다. 종목 화이트리스트는 없지만, 종목분석 **목록 외 문서는 들어오지 않는다**. 페이지당 100건·최대 20페이지이며 당일 이전 날짜를 만나면 중단한다.
- 9/22 작업은 20건을 다운로드하고 정상 종료했다. 그날 모바일 종목분석 목록의 피에스케이(319660)는 0건. 삼성증권 9/22 원문은 74쪽짜리 `Terafab` **섹터 보고서**이며 피에스케이 개별 분석은 34쪽부터다. 원문: https://www.samsungpop.com/common.do?cmd=down&contentType=application/pdf&inlineYn=Y&saveKey=research.pdf&fileName=2020/2026092109020833K_02_07.pdf
- BNK투자증권 8/18 피에스케이 단독 PDF는 원문에 존재하지만, 같은 날 확인한 네이버 모바일 **종목분석**의 피에스케이 항목은 신한투자증권 1건뿐이었다. BNK 원문: https://www.bnkfn.co.kr/uploads/85072/1/221172_493.pdf . BNK 자료가 네이버 목록에 없는 **이유 자체**는 확인되지 않았다.
- `etl/exports/stock_reports/피에스케이_319660/`에 현재 확인한 PDF는 8/18 신한 1건이다. `report_metrics.sqlite3`의 `report_facts`에도 해당 신한 보고서가 있다. 즉 다운로드/저장 전체가 고장 난 것은 아니다.
- 웹 리포트 탭은 **로컬 DB·저장 PDF를 검색하지 않는다**. `api/routers/research.py`가 `download_naver_research.list_stock_reports()`(공용 함수)로 옛 `finance.naver.com/research/company_list.naver` HTML을 다시 가져온다. 현재 해당 주소는 `stock.naver.com/research/company`로 이동했고 옛 `<tr>` 파서는 0건을 반환한다. 따라서 저장된 신한 1건도 화면에서 0건으로 보인다. 같은 함수를 쓰는 **수동 선택 다운로드 작업(`research.py` `_run_job`)과 CLI `--stock` 모드도 함께 0건**이다. 이것은 일일 배치의 수집 범위와 **별개의 종목별 조회 경로 결함**이다.
- 일일 배치 `run()`은 `report_api_facts.report_date`와 PDF 경로 날짜를 행의 `writeDate`가 아니라 **인자 `date_kst`**로 채운다. 현재는 정확히 일치 조회라 무해하지만, 여러 날짜를 훑는 순간 발행일 오기록·파일명 불일치로 중복 다운로드가 생긴다.
- `list_reports()`는 `max_pages`(20)에 닿아도 경고 없이 반환한다(조용한 절단).
- `report_api_facts`는 `run_swing_pick.py`·`swing_pick/judge_jev.py`가 읽는다. 이 테이블에 들어가는 행이 늘면 스윙 후보 입력이 바뀐다.
- `report_metrics.sqlite3`의 `report_facts`, `report_api_facts`, `report_estimates`는 현재 **종목코드당 단일 종목 보고서**를 전제한다. `run_report_metrics.py`는 `stock_reports/<종목>_<코드>/<날짜>_...pdf` 구조만 스캔한다. 섹터 PDF를 종목별 폴더에 중복 복사하거나 해당 파서에 그대로 넣으면 오분류/목표가 오류가 난다.
- 위 파일들의 실제 구현을 우선한다. 오래된 `docs/done/PLAN_STOCK_REPORT_UI.md`의 파일명 설명(`researchId`)은 현재 코드의 `pdf_key`/PDF stem 규칙과 다르다.

## 2. 목표 범위와 비목표

### 목표

1. **전 종목:** 특정 종목을 골라 받는 것이 아니라, 승인된 수집원의 발행 목록 전체를 훑고 6자리 종목코드가 지정된 **모든 종목분석** 원문 PDF를 보존한다. 기존 네이버 모바일 종목분석을 유지한다. 네이버에 없는 증권사 단독 원문(BNK 사례)은 직수집 보류로 범위 밖(§8-4).
2. **섹터/산업:** 증권사 섹터 PDF를 **문서 1건으로 저장**한다. 여러 종목 언급은 별도 관계로 연결하되 단순 언급과 심층 분석을 구분한다.
3. **발행 시차와 감사:** 최근 며칠을 중첩 재조회하고 출처별 페이지 완료 여부·발견/저장/실패 건수를 남긴다. `0건`과 `조회 실패`를 구분한다.
4. **검색 진실성:** 3100 화면은 먼저 저장된 문서 카탈로그를 검색하고 다운로드 상태/출처/문서 유형을 보여준다. 실시간 원천 검색은 별도 보조 기능으로 분리한다.

### 비목표·제약

- '전 세계 모든 증권사의 비공개·유료 PDF까지 100% 보장'하지 않는다. **출처 목록과 해당 출처 내 수집 완전성**을 명시한다. 출처가 존재해도 네이버에 유통되지 않는 보고서는 해당 증권사 채널의 안정적인 목록/이용 조건을 확인하기 전까지 자동 수집을 보장할 수 없다.
- 라이선스·로그인·robots·요청 제한을 우회하지 않는다. 증권사 직수집은 허용된 공개 원문만 대상으로 승인된 출처별로 추가한다.
- 섹터 보고서의 회사 언급만으로 개별 종목 투자의견·목표가·상향 신호를 생성하지 않는다. 기존 트레이딩·swing-pick의 후보 선정 규칙은 건드리지 않는다.
- 원본 원문 PDF, 발견 메타, 수치 추출 결과의 **단계별 성공**을 구분한다. PDF 다운로드 성공 = 목표가 파싱 성공이 아니다.

## 3. 출처/수집 정책

| 단계 | 수집원 | 문서 범위 | 검증 방법 |
|---|---|---|---|
| A: 현행 유지·보강 | 네이버 모바일 `/api/research/company` 목록+상세 | 종목코드 지정된 종목분석 | 날짜별 페이지 종료까지 목록 수와 카탈로그 발견 수 대조; PDF 미첨부 별도 상태 |
| B: 섹터·시황 (실사 완료 §6-1) | 네이버 모바일 `/api/research/{industry,market,invest,economy}` 목록+상세 (`debenture`는 §8-1 범위 밖) | 종목코드 없는 산업·시황·전략·경제 PDF | 날짜별 페이지 종료까지 목록 수와 카탈로그 발견 수 대조. `company`와 같은 방식 |
| C: 직수집 어댑터 — **보류(§8-4)** | 승인된 증권사별 공개 리서치 목록(우선 삼성증권·BNK 사례) | 네이버에 없는 종목/섹터 문서 | 재개 시: 사례별 출처 조회·PDF 원본 검증·네이버와 중복 대조. 증권사별 이용 조건과 목록 완전성 표기 |

- 발견 데이터에는 `source`, `source_report_id`, 원문 목록 URL, 상세 URL, PDF URL, `published_at`/원문 표기일, `first_seen_at`, `last_seen_at`, 발견 배치 ID를 남긴다. 발행일과 실제 최초 발견일을 절대로 같은 의미로 쓰지 않는다.
- 대상일 **정확히 일치** 조회만 하지 말고 중첩 기간(초기 제안: 최근 7일, 최종 설정은 소스 지연 관측으로 결정)을 매번 다시 훑는다. 재실행 시 기존 문서는 스킵/메타 갱신만 한다. 장기 과거분 백필은 하지 않는다(§8-5).
- 출처의 날짜 정렬·페이징이 깨지거나 설정한 최대 페이지에 닿으면 `completed`가 아닌 `partial/error`로 기록한다. HTML/JSON이 다른 페이지로 이동한 경우 200 응답만으로 성공 처리하지 말고 예상 필드/목록 구조를 검증한다.
- 다운로드: `%PDF` 서명 외에 HTTP 상태, MIME/용량, PDF 열람 가능 여부를 확인한다. 실패/미첨부/권한 제한을 항목별로 기록하고 재시도·속도제한·일별 보고에 반영한다. 증권사 자체 링크가 유효하지 않으면 성공으로 세지 않는다.

## 4. 카탈로그·원본·중복·섹터 연관관계

**논리 모델** (확정: 기존 `etl/db/report_metrics.sqlite3` **같은 파일**에 아래 4개 테이블 추가. 별도 DB 파일 만들지 않음. 기존 3개 테이블 스키마는 변경하지 않음):

- `report_documents`: 내부 `document_id`, `document_type`(company(종목)/industry(산업·섹터)/market(시황)/invest(투자전략)/economy(경제)/unknown — 네이버 카테고리와 1:1, `catalog.py` CHECK 제약과 동일. 별도 `sector` 값은 없다, §8-1), 제목, 증권사, 발행일, PDF 상대경로, 내용 해시, 원본 저장/열람 상태, 파싱 상태, **`pdf_key`(nullable, UNIQUE)**. `unknown`도 버리지 말고 검토 대상으로 둔다.
  - **기존 테이블과의 연결:** 네이버 출처 문서는 `pdf_key`를 채우고, 기존 `report_facts`/`report_api_facts`/`report_estimates`는 `pdf_key`로 조인한다(1:1). 기존 테이블에 `document_id` 컬럼을 추가하지 않는다. 네이버 섹터·시황 문서도 `pdf_key`는 채우지만(§6-1) `document_type != company`이므로 기존 테이블에 행을 만들지 않는다. 기존 테이블 적재 여부는 `pdf_key` 유무가 아니라 `document_type`으로 가른다.
  - **1:1 예외 (2026-09-29 실측):** 네이버가 같은 PDF 바이트를 다른 날짜·다른 `pdf_key`로 재게시한 사례 14건(기존 2,392파일 중). 해시 기준으로 문서는 1개로 합쳐지고 `report_documents.pdf_key`에는 첫 키만 남는다. 따라서 **`pdf_key` → 문서 조회는 `report_documents.pdf_key` 다음에 `report_sources`(URL/경로에 키 포함)까지 본다.** 조회 코드 작성 시(§6-6) 적용.
- `report_sources`: `(source, source_report_id)` 유일 키 + `document_id` 외래키, 외부 URL들, 발견 시각/상태. 여러 출처가 같은 PDF에 연결돼도 **원본 문서는 하나**만 둔다. 기존 네이버 `researchId`와 증권사 자체 ID는 전역 유일 키로 혼용하지 않는다.
- `report_document_stocks`: `(document_id, stock_code)` 관계 + `relation_type`(주요 분석/단순 언급/미확인, 판정 규칙 §8-6), 근거 페이지 범위, 식별 방법, 검토 상태. 종목코드가 PDF 본문에 나타나도 **그 종목에 대한 투자 의견이 제시된다는 의미는 아니다**.
- `report_collection_runs`: 수집원/기간/시작·완료 시각, API 페이지 수와 원천 항목 수, 발견/중복/다운로드/실패/미첨부, 종료 사유와 마지막 성공 페이지. 누락 의심·소스 변경 알림의 근거로 쓴다.

**동일성:** 기존 네이버의 `pdf_key`(pstatic 파일 stem)는 **기존 단일종목 데이터와의 호환키**로 유지한다. 다중 출처 문서의 기본 식별은 원본 PDF 바이트의 SHA-256과 출처 ID/URL 매핑으로 설계한다. **판정 순서:** ① `(source, source_report_id)`가 이미 있으면 다운로드 없이 `last_seen_at`만 갱신 → ② 없으면 PDF 다운로드 → ③ SHA-256이 기존 문서와 같으면 `report_sources` 행만 추가하고 새 파일은 버림 → ④ 다르면 새 문서로 저장. 단, 게시 시각·표지/워터마크만 바뀐 같은 내용은 해시가 달라질 수 있으므로 동일 제목·증권사·날짜 후보를 **검토 대상**으로만 표시하고 자동 병합하지 않는다. 파일 저장은 `exports/stock_reports/`의 기존 레이아웃을 보존하고 섹터 원본은 별도 `exports/sector_reports/` 아래 한 번만 저장한다(구체 파일명은 안전한 내부 ID와 날짜로 구성). 서로 다른 URL로 재배포된 동일 바이트는 원본 중복 저장하지 않는다.

**분석 경계:** 기존 `report_facts`/`report_api_facts`/`report_estimates`를 섹터 PDF에 직접 업서트하지 않는다. 섹터 본문에서 특정 종목의 명시적 목표가를 추출·반영할지는 아래 결정사항을 승인받은 뒤 별도 종목-문서-페이지 단위 검증 파이프라인으로 설계한다. 이미 저장한 단일종목 리포트와 섹터 내 동일 문장의 중복 목표가도 구별해야 한다.

## 5. UI/API 계약 방향

- `GET /research/stock/{code}/reports`: **로컬 카탈로그가 권위 소스**. 저장된 개별 보고서와 연관된 섹터 문서를 통합 표시하되 `document_type`, `source`, `relation_type`, `download_status`, `parse_status`, 발행일, PDF 열람 링크를 분리한다. 새 API 버전 또는 호환 필드를 두고 기존 응답 소비자/선택 다운로드 UX는 회귀 테스트로 지킨다.
- `GET /research/documents/{id}` 및 `/pdf`: 서버가 내부 `document_id`로 경로를 찾고 경로 탈출을 막는다. 현재처럼 클라이언트가 `writeDate/brokerName/pdfKey`를 조합해 PDF 경로를 추측하는 방식은 새로운 출처·섹터 파일에 사용하지 않는다.
- 별도 **원천 검색** 버튼/메서드는 '미수집 보고서 발견/다운로드' 용도로 분리한다. 외부 장애 시 저장된 문서가 UI에서 사라지면 안 된다. `없음(카탈로그 0)` / `원천 미조회` / `조회 실패` / `검색 범위 밖` / `섹터 관련문서`를 다른 상태로 표시한다.
- 3100 종목 분석 허브의 검색 범위(기간, 증권사, 출처, 회사보고서·섹터)와 상태를 명시한다. 피에스케이홀딩스(031980)는 피에스케이(319660)에 자동 병합하지 않는다.

## 6. 단계별 구현 순서 (다른 에이전트 인계)

0. **UI 0건 선행 제거 (카탈로그와 독립, 최소 변경):** `GET /research/stock/{code}/reports`가 원천 HTML 대신 로컬 `exports/stock_reports/<종목>_<코드>/` 파일과 `report_api_facts`를 읽어 반환하게 한다. 응답 필드(`pdfKey`/`writeDate`/`brokerName` 등)는 유지해 웹 수정 없이 저장된 PDF가 보이게 한다. 수동 다운로드·`--stock` 모드는 원천이 죽어 있으므로 이 단계에서 '원천 미지원'으로 명시적 오류를 반환하게 하고, 복구는 6단계로 넘긴다. 검증: 319660 조회 시 8/18 신한 1건 표시.
1. **수집원 실사 — 네이버 완료 (2026-09-29):**
   - 모바일 API에 카테고리 목록이 있다. 목록 행·상세(`researchContent.attachUrl`)·PDF(pstatic) 구조가 `company`와 같다.

     | 경로 | `researchCategory` | `attachUrl` 예 |
     |---|---|---|
     | `/api/research/industry` | 산업분석 (`category`=반도체 등 업종) | `.../industry/66/20260929_industry_638804000.pdf` |
     | `/api/research/market` | 시황정보 | `.../market/66/20260929_market_982172000.pdf` |
     | `/api/research/invest` | 투자전략 | `.../invest/15/20260929_invest_449916000.pdf` |
     | `/api/research/economy` | 경제분석 | `.../economy/39/20260929_economy_238494000.pdf` |
     | `/api/research/debenture` | 채권 (범위 밖) | 미확인 |

   - **식별자:** `researchId`는 카테고리별 번호라 전역 유일 아님(예: industry 46255, economy 13858). `source_report_id`는 `{카테고리}:{researchId}`로 저장. `pdf_key`는 파일명에 카테고리가 들어가 전역 유일 → 섹터·시황 문서도 `pdf_key`를 채운다(단, §4 분석 경계대로 기존 목표가 테이블엔 넣지 않음).
   - **양:** 산업분석 최근 500건 ≈ 27영업일(하루 ~18건). 7일 중첩 재조회도 현행 상한(100건×20페이지) 안.
   - **커버리지 빈틈:** 산업분석 최근 500건에 삼성·미래에셋·KB·NH·메리츠 **0건**. 종목분석 최근 800건(~7주)도 삼성 10·메리츠 2·KB·NH 0건. 삼성 9/22 `Terafab`은 네이버 어느 카테고리에도 없음 → 대형사 리포트 대부분이 수집 범위 밖(§8-4).
   - **증권사 직수집 시도 중단:** 삼성 리서치 탐색기(`research_pop.jsp`, robots 전체 허용)는 POST 서버 렌더 목록이지만 카테고리·날짜 파라미터를 역추적해야 했고 3회 시도로 실패. 사이트 변경 시 조용히 0건이 되는 구조라 유지보수 대비 이득이 작다고 판단(사용자) → 보류 유지.
   - 남은 작업: §8-6 규칙을 네이버 산업분석 PDF 3개 증권사 이상으로 재확인.
2. **카탈로그 선행:** 기존 파일/`report_facts`를 읽어 카탈로그에 안전하게 편입하는 멱등 마이그레이션 설계. 원본 파일/기존 목표가 데이터를 수정·삭제하지 않으며, `pdf_key` 호환성과 종목코드 6자리 문자열(선행 0 포함)을 유지한다. 테스트에서 기존 8/18 신한 PDF가 그대로 노출되는지 검증.
3. **현행 종목 배치 확장:** `download_naver_research.py`의 모바일 API 수집을 유지하고, 목록/상세/PDF 단계별 결과를 카탈로그에 남긴다. 중첩 재조회·페이징 완료 신호·결측 재시도 추가.
   - **날짜 기준 교체:** `report_api_facts.report_date`와 PDF 경로 날짜를 인자 `date_kst`가 아니라 각 행의 `writeDate`로 채운다. 테스트: 7일 재조회 시 과거 리포트의 `report_date`가 발행일이고, 같은 PDF가 두 번 저장되지 않음.
   - **페이지 상한 도달:** 마지막 페이지까지 대상 기간을 벗어나지 못하면 `report_collection_runs`에 `partial`로 남기고 `notify()`로 경고한다. 7일×일 수백 건 기준 상한(현재 100건×20페이지)이 충분한지 실측 후 조정.
   - **스윙 입력 변화 인정:** 누락분이 `report_api_facts`에 추가되면 스윙 후보 입력이 바뀌는 것은 의도된 결과다. 금지 대상은 섹터 문서 유입뿐이다(§7).
   - Windows 등록 작업과 기존 `notify()`/Discord 전송 규칙을 활용하고 다른 작업 스케줄은 바꾸지 않는다.
4. **섹터 문서 수집:** 네이버 `industry`/`market`/`invest`/`economy` 목록을 `company`와 같은 루프로 돈다(카테고리만 파라미터). 목록 어댑터에서 PDF를 **한 건만** 저장하고 타입을 붙인다. 먼저 전체 텍스트/표지를 보관·검색 가능하게 한다. 종목 연계는 §8-6 규칙으로 판정하고 페이지 근거·검토 상태를 둔다. 삼성 9/22 PDF를 테스트 픽스처로 쓴다. OCR은 하지 않는다(§8-5).
5. **증권사별 빈틈 메우기 — 보류(§8-4):** 재개 시 삼성·BNK 등의 **실제로 확인된** 공개 출처별 어댑터를 추가한다. 네이버 목록에 없던 두 원문이 카탈로그에 들어오고 기존 리포트와 중복 다운로드되지 않는지 검증. 미지원 증권사는 '미지원'으로 남긴다.
6. **API/화면 변경:** `api/routers/research.py`, `broker-web/components/stock/research-tab.tsx`를 카탈로그 기반으로 바꾸고, PDF 보기 경로를 새 문서 ID와 연동한다. 수동 선택 다운로드·진행률은 원천(`list_stock_reports`)이 이미 깨져 있으므로 '유지'가 아니라 **새 원천(모바일 API 종목 필터 또는 카탈로그 원천 검색)으로 재구현**한다. 새 원천 확보 전에는 0단계의 명시적 오류를 유지한다. API(:8000)와 웹(:3100)의 로컬 실행으로 검증한다.
7. **범위 보고 (백필 없음, §8-5):** 출처별 신규 적재/결측/실패 수치를 보고한다. 운영 시작일을 카탈로그 커버리지 시작일로 명시한다. 단, 기존 `exports/stock_reports/` 파일은 2단계 마이그레이션으로 카탈로그에 편입한다(재다운로드 아님).

## 7. 필수 검증 시나리오/운영 성공 기준

- **사례 회귀:** 2026-08-18 신한 피에스케이(319660) 1건은 로컬 카탈로그·화면에 표시. BNK 8/18은 직수집 보류로 검증 대상 아님. 삼성증권 9/22 `Terafab` 섹터 PDF 1건(픽스처)은 섹터로 판정되고 HPSP·피에스케이·파크시스템스가 `주요 분석`(근거 p26·p34·p42~), 삼성전자/인텔 등은 `단순 언급`이어야 한다. p4·p5·p24 요약표 등장만으로 `주요 분석`이 되면 실패. 피에스케이홀딩스(031980)는 섞이지 않아야 한다.
- **멱등:** 같은 문서를 다른 출처나 다음 날 재조회해도 원본·카탈로그·연관관계의 중복이 증가하지 않아야 한다. 메타데이터 최신화는 출처 이력으로 추적 가능해야 한다.
- **발행 지연:** 어제 보고서가 오늘 목록에 처음 올라와도 중첩 재조회로 수집된다. 날짜가 되돌아가거나 오래된 보고서가 재등장하면 페이지 경계로 조기 종료하지 않도록 검증한다.
- **장애/무음 회피:** 외부 페이지가 리다이렉트·HTML·빈 JSON·권한 오류를 반환하면 '정상 0건'이 아닌 원천 장애/부분 완료로 기록. PDF 없는 행, 깨진 파일, 잘못된 종목 연계도 별도 상태로 남긴다. 로그의 `listed`만으로 완전 수집을 주장하지 않는다.
- **데이터 안전:** 섹터 문서의 종목 언급이 `report_api_facts` 목표가 상향 이벤트로 들어가지 않아야 한다. `document_type != company` 문서(섹터·시황, `pdf_key` 있어도)는 `report_facts`/`report_api_facts`/`report_estimates`에 한 행도 추가하지 않아야 한다. 네이버 종목분석 누락분 보강으로 스윙 입력이 늘어나는 것은 허용한다(§6-3).
- **UI:** 원천 장애 상태에서도 저장된 PDF 검색·열람이 된다. 원천 0건, 로컬 0건, 다운로드 실패를 구분해 표시한다.
- **운영 보고:** 작업 종료 메시지에 '원천 목록 수/코드 없는 섹터 후보 수/신규 문서/중복/실패/미첨부/부분 완료/출처별 커버리지'를 분리 표시하고, DB/원본 파일 수와 대조한다.

**예상 검증 명령(구현 후, 프로젝트 루트):** 기존 다운로더 테스트는 `PYTHONPATH=etl uv run --project etl python -m unittest discover -s etl/tests -p test_download_naver_research.py`로 실행한다. 새 카탈로그/출처 테스트는 `etl/tests/test_report_catalog*.py`로 만들고 같은 `unittest discover`로 실행한다(etl 규약은 unittest). API 테스트는 기존 `api/test_research.py`를 확장하고 `api/`에서 `uv run --with pytest --with httpx pytest test_research.py`로 실행한다(api는 pytest+monkeypatch 규약). 웹은 `npm --prefix broker-web test -- __tests__/research-tab.e2e.spec.ts`(현재 존재하는 Playwright 시나리오)를 우선 사용한다. 명령 성공만으로 배포 검증을 갈음하지 말고 실제 8000/3100 GET·PDF 링크·다음 정기 작업 로그를 대조한다. **현재 문서 작성 단계에서는 테스트/배치를 실행하지 않았다.**

**6. 관계 판정 규칙** (삼성 9/22 `Terafab` 74쪽 텍스트 실측 근거):

- `주요 분석`: 어떤 페이지의 **맨 윗줄이 `회사명 (6자리코드)`** 이고 **같은 페이지에 `투자의견`과 `목표주가`** 가 있음. 근거 페이지 = 그 페이지부터 다음 `주요 분석` 시작 전까지.
  - 실측: p26 `HPSP (403870)`, p34 `피에스케이 (319660)`, p42 `파크시스템스 (140860)` 3건 모두 해당, 오탐 없음.
- `단순 언급`: `주요 분석` 페이지는 없고 본문에 코드 또는 `stock_names` 회사명이 나옴.
  - 실측: p4·p5·p24 요약표에 위 3종목 코드가 다 나옴 → **코드 등장만으로 `주요 분석` 판정 금지**.
  - 삼성전자·인텔 등은 코드 없이 이름만 나옴 → 회사명 검색 필요. 2~3글자 짧은 이름(예: `SK`)은 오탐 위험 → 단어 경계 일치 + 짧은 이름 제외 목록.
