# 급등 전 변화 포착 — 예약 등록안 (PLAN §20-5)

- 작성 2026-09-09. 근거는 실측이며 추정치가 아니다. policy_v2 기준.
- 이 문서는 **등록안**이다. 실제 Windows Task Scheduler 등록·외부 발송·주문 연동은 하지 않는다(§1.3).
- 등록 시 `ops/batches/README.md` 의 전략별 작업 매핑과 레지스트리 절차를 따른다.

## 1. 결론 — policy_v2 한도로 일일 운영 가능

```
하루 신규 유입   429.1건  (텔레그램 393.2 + 리포트 35.9, 최근 30일 실측)
처리 한도        600건 / 150분 (§12.2 policy_v2)
순처리량         +170.9건/일   → operations_ready: true
```

### policy_v1 에서는 불가능했다

```
policy_v1  300건/90분 → 순처리량 -129.1건/일 → operations_ready: false
```

병목이 **시간이 아니라 호출 상한**이었다. 90분으로 시간상 452건까지 가능한데 호출 상한
300에 먼저 걸렸다(`binding_limit: calls`). §12.3 규정대로 완료 시점을 산출하지 않고
`backlog_growing` 으로 표시했고, 그 실측을 근거로 한도를 올렸다.

이 한도는 codex 계정 사용량과 무관한 **자체 예산**이다. §12.2 에 적어 둔 숫자이며
한 번의 실행이 무한정 도는 것을 막는 용도다.

## 2. 실측 단가

| 모델 | 표본 | p50 | p95 | 평균 입력 |
|---|---:|---:|---:|---:|
| codex 기본(gpt-6-astra) | 300 | **11.93초** | 43.79초 | 437자 |
| gpt-5.6-luna | 300 | **15.76초** | 132.16초 | 1,327자 |

- luna 가 느려 보이는 건 모델 탓이 아니다. 8월 표본에 리포트 PDF 가 섞여 **입력이 3배**다.
  자당 처리속도는 luna 가 오히려 빠르다(0.0119초/자 vs 0.0273초/자).
- p95 가 p50 의 3~8배다. 긴 리포트 한 건이 예산을 크게 먹으므로 **시간 상한을 함께 두는 현재 방식이 맞다.**

## 3. 한도 조정안

| 설정 | 일 처리 | 병목 | 순처리/일 | 판정 |
|---|---:|---|---:|---|
| policy_v1 300회/90분 | 300 | calls | **-129.1** | 적체 증가 |
| 450회/90분 | 450 | time | +20.9 | 겨우 균형 |
| **policy_v2 600회/150분** | **600** | calls | **+170.9** | **채택** |
| ㄴ luna 로 돌릴 때 | 571 | time | +141.9 | 여유 |

**채택: 600회 / 150분 / 하루 1회.**

- 두 모델 모두 순처리량이 양수라 어느 쪽으로 돌려도 적체가 줄어든다.
- 하루 2회로 나누는 안도 검토했으나(300×2 = 같은 600건) 실행을 하나로 두는 편이
  스케줄과 lease 관리가 단순하다. p95 가 132초라 긴 리포트가 몰리면 시간 상한에
  먼저 걸리는데, 그때는 남은 항목이 `deferred` 로 다음 실행에 넘어간다(§12.2).
- 순처리량 +170.9건/일이면 초기 적체(39,544건)를 **약 231일**에 해소한다. 초기 적재를
  앞당기려면 별도 백필 실행을 며칠 돌리는 편이 낫다.
- policy_v1 → **policy_v2** 로 기록한다(§21.1 조정 가능 항목).

### 캐시 키를 함께 고쳤다

정책 버전을 올리면 `processing_results` PK 에 `policy_version` 이 들어 있어 이미 추출해 둔
600건이 통째로 무효화되고 2.5시간을 다시 호출해야 했다. 추출은 "무엇을 뽑는가"이고
처리 한도는 "몇 건 처리하는가"라 서로 무관하므로 단계별로 키를 갈랐다(§14).

```
판단(assess)  입력해시 + 프롬프트 + 모델 + 정책 + 코드
1차 추출       입력해시 + 프롬프트 + 모델 + 코드      (storage.EXTRACT_CACHE_POLICY)
```

## 4. 등록안

| 작업 | 시각(KST) | 명령 | 비고 |
|---|---|---|---|
| 수집 | 09:30 | `--stage capture` | 전일 수집분과 최신 완료 일봉 |
| 추출 | 09:35 | `--stage extract --limit 600` | 최대 150분. 초과분은 deferred |
| 평가·보고서 | 12:30 | `--stage assess` | LLM 미호출 |
| 주간 선정 | 화 12:40 | `--stage assess` 후 주간 결과 확인 | §12.1 |
| 성과 평가 | 월 17:00 | `--stage evaluate` | LLM 미호출 |
| 처리량 점검 | 월 17:10 | `--stage capacity` | 한도 재검토 |

작업 디렉터리는 `etl/`, 실행기는 `.venv\Scripts\python.exe scripts\run_early_signals.py` 다.

### 선행 조건

- 상위 수집이 끝난 뒤여야 한다. `--stage capture` 는 `telegram_public.sqlite3` 와
  `exports/stock_reports` 를 읽으므로 그 수집 배치보다 뒤에 둔다.
- 일봉은 마지막 **완료** 거래일만 쓴다(§9). 오전 실행은 당일 일봉이 확정되기 전이라
  가격 기준일이 전일이 된다 — 정상 동작이다.
- 완료되지 않았으면 degraded 로 처리하고 결과에 표시한다.

## 5. 모의 실행 결과 (연속 5회)

```
run1: 1s processed=60 cached=60 events=95 errors=0
run2: 1s processed=60 cached=60 events=95 errors=0
run3: 1s processed=60 cached=60 events=95 errors=0
run4: 1s processed=60 cached=60 events=95 errors=0
run5: 1s processed=60 cached=60 events=95 errors=0
```

- 5회 모두 **같은 이벤트 수**가 나왔다. 식별키가 결정적이라 재실행이 중복을 만들지 않는다(§6.4).
- 캐시 적중 60/60 으로 LLM 재호출이 없었다. 중단 후 재개해도 이미 처리한 원문을 다시
  부르지 않는다(§14).
- 오류 0건.

단 이 5회는 **캐시 적중 상태의 안정성**을 본 것이다. 신규 원문에 대한 연속 5회 실측은
실제 등록 후 첫 주에 다시 재고, 그때 §12.2 한도를 확정한다.
